## 二、决定性发现：复位根本没跑

严格回放**成功返回**（`baseKind: full_checkpoint`，不抛错），但**输出表头仍是畸形形态**：

```
sheet_dCudvUnH: header=["row_id",null,"主角当前所在地点","当前时间","上轮场景时间","经过的时间"]
sheet_in05z9vz: header=["row_id",null,"物品名称","数量","描述/效果","类别"]
…（9 张全部如此）
```

**根因（代码级确证）**：`normalizeLegacyDuplicateCheckpointState_ACU`
（`storage-frame-v2-replay.ts:1325`）的流程是

```
restoreLegacyRowIdentity_ACU(state)
  const probe = deepClone(state)
  normalization = normalizeCanonicalTableRows_ACU(probe)
  if (removedRows>0 || 非重复类 errors>0) → normalizeHistoricalReplayState_ACU(...)  // ← 复位只在这条支路
  audit = auditTableDataForUpgrade_ACU(state)
  if (audit.status === 'clean' && normalization.errors.length === 0) {
      replaceState_ACU(state, probe); return;        // ← 本聊天走这条：提前返回
  }
```

畸形表头对这两道判据都**不构成问题**：`normalizeCanonicalTableRows_ACU` 只看 row_id 是否存在/重复与行宽，
`auditTableDataForUpgrade_ACU` 不看列名合法性 ⇒ `audit.status==='clean'` ⇒ **提前返回**
⇒ S3.2a 加在 `normalizeHistoricalReplayState_ACU` 里的复位**在本聊天上永不执行**。

## 三、失败的真实触发点

回放本身不抛错；失败发生在**写入侧**：

1. 手动重填以 runtime 基底生成 operations，追加进候选 chat；
2. 写时严格探针（`storage-frame-v2-persist.ts:679` `validateAppendedOperationsReplayCandidate_ACU`）
   重放候选 chat —— 此时多了一条 `sql_batch`，回放它要建别名表
   （`buildReplaySqlTableAliases_ACU` → `resolveSheetColumns_ACU` → `resolveEffectiveDDL`
   → `generateFallbackDDL`），在**仍未复位**的畸形表头上撞 `empty_column_name`；
3. 探针抛错 → `buildAppendedOperationsWriteRejectionMessage_ACU` ⇒ 真机文案
   「V2 写入被拒绝：… fallback DDL 表头不合法：第 2 列「」empty_column_name」**逐字吻合**。

## 四、结论与落点修正

- **S3.2a 的落点不够早**：必须在**回放基底构造处**复位，而非仅在
  `restoreLegacyRowIdentity_ACU` 之前的历史兼容支路。
- **修正落点**：
  1. `normalizeLegacyDuplicateCheckpointState_ACU` **函数首**（原地、先于 `restoreLegacyRowIdentity_ACU`）
     —— 覆盖 full checkpoint（`:2411`）与 replacement anchor（`:2384`）两条基底构造；
  2. `applySheetCheckpointsForReplay_ACU`（`:1626` 取 `checkpoint.data` 后）—— 同缺陷类，按单表复位；
  3. 保留 `normalizeHistoricalReplayState_ACU` 内的一处（覆盖 operation 级候选及其余支路，幂等无副作用）。
- **D-C′ 次落点（5 处 `resolveEffectiveDDL` 调用点）判定：全部不动。** 理由：它们消费的都是
  **已由基底/ hydrate 复位过的状态**，复发点唯一在「基底未复位」；在消费侧复位反而会改写只读快照
  （`sql-table-service.ts:2512` 的 before 快照）、presentation 透传副本（`name-mapper.ts:208`）、
  best-effort 探测器（`template-import-validator.ts:106` 自带 try/catch 且注释明令不得升级为导入失败）。
  逐条论证见 `implement.md` S3.2b。
